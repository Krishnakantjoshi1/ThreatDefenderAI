History/reports:
- `GET /api/history` with bounded pagination.

SHARED BASELINE / API CONTRACT
Follow these routes unless the existing app already has compatible routes. If it does, preserve them and document the real route/payload in `docs/api-contract.md`; frontend should not have to guess.

Auth/session:
- `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`.
- Restrict first-run setup safely (only while no users exist) and require authenticated/admin-controlled account creation afterward if multi-user account creation is supported. No open privileged registration.
- Use established password hashing; don't store plaintext passwords. Use server-managed sessions/cookies where suitable, expiration/revocation/rotation, secure cookie attributes in the supported local deployment, and CSRF safeguards where applicable. For extension access, use a deliberately paired/revocable scoped token only if needed; never expose global server secrets.

Single scan:
- Keep current route if compatible. Fallback: `POST /api/scans` with validated `{type: "url" | "text" | "message", value: "..."}`. Upload files via bounded multipart handling; never accept a user-provided local filesystem path.

Batch jobs:
- `POST /api/scans/batch` accepts `{items: [{type, value, client_ref?}], options?: {...}}` and returns `{job_id, status, total, completed, failed, ...}`.
- Support 100+ items in one batch request. Apply a configurable hard limit (for example 500 inputs/request), byte-size limits, validation, rate/queue bounds, and clear `413`/`429`/`503` behaviour. Never accept unbounded queues or create one unbounded async task per input.
- Default max concurrent scans is 10 and processing chunk size is 10, both centrally configured. Keep work bounded with an asyncio semaphore/queue or an appropriate mechanism already in the project. Do not add Redis/Celery by default.
- `GET /api/scans/jobs/{job_id}` gives progress only to the owner.
- `GET /api/scans/jobs/{job_id}/results?limit=...&offset=...` provides bounded paginated per-item outputs; one input error must not crash the entire batch.
- `POST /api/scans/jobs/{job_id}/cancel` allows only the owner to request cancellation.
- Expose consistent status, totals, completed, succeeded, failed, pending/running where meaningful, timestamps and terminal states (e.g. `completed`, `completed_with_errors`, `failed`, `cancelled`). Document actual values.
- Reuse database persistence if available. For an in-process queue, bound it and document restart behaviour honestly; on restart, mark orphaned in-progress jobs as interrupted/failed rather than stuck forever. Do not claim durable queue semantics unless implemented.

User isolation — REQUIRED, NOT OPTIONAL:
1. Establish a real authenticated principal on every protected request. A UUID, profile hash, cookie value supplied without validation, localStorage entry, job ID, scan ID, or frontend user_id is NOT authentication.
2. Add a durable owner/user key to every user-owned record (scans/history, jobs, individual job results, settings, quarantine metadata, reports/exports and any user-specific threat memory). Public/global threat lists may remain global only if they contain no user's private content.
3. Enforce ownership in repository/query/service layer on every access, not just route/UI layer. Fetch by `(resource_id, authenticated_user_id)` where possible. Never fetch arbitrary objects by ID and check later as the only control.
4. Apply isolation to read, create, update, delete, cancel, retry, export, restore, and bulk operations. A job's child results inherit and must be checked against the same owner.
5. Keep per-user quarantine/runtime files under separate runtime directories keyed by an internal opaque owner identifier, with safe path joins and no user-controlled path traversal. Do not rely on directory names as proof of authorization.
6. Do not write full private message contents, session credentials, API keys, or raw secrets into shared logs. Redact sensitive values; logs, errors, temp files and generated PDFs must not bypass access control.
7. For an unauthorized or other-user object ID, return a non-leaking response (consistent 404 is acceptable) and do not confirm that another user's record exists.
8. Add tests with users A and B proving B cannot read/list/cancel/change/export/delete A's scans, jobs/results, history, settings, quarantine entries or reports. Test both endpoints and lower-level query/service paths.
9. If the current project has no authentication, do not fake security by adding profile IDs. Implement a minimum credible local authentication/session design compatible with the app, or record a specific blocker/design decision before modifying persistence. Preserve existing data via a migration/backup; do not silently delete records.

PDF EXPORTS:
- Implement `GET /api/reports/scans/{scan_id}.pdf` and `GET /api/reports/history.pdf` or document compatible existing alternatives.
- Generate PDF content exclusively from records authorized for the current user. Escape/untrusted text, avoid loading remote URLs/content while generating a report, constrain report size and temp-file storage, set correct content type/download filename, and clean temporary files safely. History PDF must include only current user's records and have a bounded/default date range or record cap to prevent memory abuse.
- Use an existing PDF dependency if appropriate; add a dependency only when justified and document installation. Never put API keys or session data in PDFs.

SECRETS, NETWORK, PRIVACY:
- Put external provider credentials only in environment/config injection on the backend; provide `.env.example` with placeholders and ensure `.env`, DBs, runtime files and generated PDFs are ignored by Git. Do not print secrets in health routes/logs/exceptions.
- Bind to loopback (`127.0.0.1`) for local mode unless the existing app's documented use requires otherwise. Use an exact, small CORS allowlist; never `*` with credentials. Validate Origin/Host where appropriate and avoid trusting arbitrary host headers. Protect localhost endpoints from website-triggered cross-origin misuse to the extent compatible with extension integration.
- Keep sensitive text local by default. Use online reputation only with appropriate indicators and only when enabled/configured; preserve current Ollama/Phi-3 integration if it exists. Handle offline/unavailable services honestly; do not falsely report online checks succeeded.
- Validate URLs and prevent backend URL fetchers from becoming SSRF tools. If current security tools fetch user-controlled URLs, reject loopback/private/link-local/metadata destinations as appropriate, handle redirects safely, and set timeouts/response limits. Do not visit links during PDF generation.
- File scanning must not execute the file. Apply size limits, safe temporary names and cleanup.
